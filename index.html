Foundations·The idea

NetBox records what your infrastructure should be. Everything else checks it.

Intended state, not observed state

Monitoring and discovery tell you what is happening. NetBox holds what you decided: the rack a server belongs in, the prefix a site was given, the circuit that feeds it.

An opinionated model

Sites, racks, devices, cables, prefixes, VLANs, circuits and virtual machines already exist, with the relationships between them. You start modelling on day one instead of designing tables.

API first

Anything you can click in the UI is available over REST and GraphQL. That is what lets automation read NetBox instead of a spreadsheet.

What community NetBox does not do

It does not poll devices, discover your network or push configuration to hardware. Those jobs belong to other tools that use NetBox as their input, which is exactly the pattern the later chapters show.

Foundations·The shape of it

A few core objects, nested the way your estate is.

Region / Site group where in the world └─ Site a building or campus └─ Location a room or cage, nestable └─ Rack with numbered units └─ Device has a role, type and status ├─ Interface ── Cable ── Interface └─ IP address, VLAN, power port

Cutting across all of it: tenants say who owns something, tags label anything, and custom fields add the attributes only you care about.

From 4.7 the nested group models (regions, locations, device roles and more) are stored with PostgreSQL ltree rather than django-mptt. Plugin authors need to know. Everyone else just gets faster tree queries.

Deploy·Quick start

Up and running in a few commands, pinned to v4.7.2-5.1.1.

terminalnetbox-docker 5.1.1
# 1. Get the netbox-docker files at the version that matches the image
git clone -b 5.1.1 https://github.com/netbox-community/netbox-docker.git
cd netbox-docker

# 2. Pin the image and publish the web port
echo "VERSION=v4.7.2-5.1.1" > .env
cp docker-compose.override.yml.example docker-compose.override.yml

# 3. Pull and start
docker compose pull
docker compose up -d

# 4. Create the first admin once it is healthy
docker compose exec netbox /opt/netbox/netbox/manage.py createsuperuser

Give it a few minutes on first start while the database migrates. Then open http://localhost:8000/. The override example maps host port 8000 to the container's 8080.

Restarting from an empty database a lot? Set the SUPERUSER_* variables in the override file instead of running createsuperuser by hand.

Deploy·Before anyone else logs in

The defaults get you running. They are not a production setup.

Where configuration lives

  • env/netbox.env, postgres.env, redis.env for settings
  • configuration/ mounted read-only at /etc/netbox/config
  • plugins.py, ldap/ and extra.py live in that folder

What persists

  • netbox-postgres the database
  • netbox-redis-data the task queue
  • netbox-media-files uploads
  • netbox-scripts-files and netbox-reports-files your custom code

Change before go-live

  • The example database and Redis passwords in env/
  • The shipped API_TOKEN_PEPPER_1, a public example value
  • CORS_ORIGIN_ALLOW_ALL=True, which is set by default
  • Mail settings, which point at localhost

Put TLS in front

The container speaks plain HTTP on 8080. Terminate TLS on a reverse proxy or load balancer, and publish only that.

Add single sign-on early

The override example ships Okta and Google environment variables, and the config folder has an LDAP slot. Adding SSO after people have local accounts is harder than starting with it.

Community NetBox 4.7.2 · netbox-docker 5.1.1
Deploy·Read this before upgrading

4.7 raised the floor, and 4.7.2 closes a token exposure.

Hard requirements

  • PostgreSQL 15 or later. 14 is dropped and the upgrade aborts on it
  • The ltree extension. NetBox installs it if the database user has CREATE on the database
  • Redis 6.0 or later. 5.x is dropped. netbox-docker uses Valkey

Plan a maintenance window

The move from django-mptt to ltree locks tables and backfills them, and the upgrade then rebuilds the config context cache with one update per device and VM. On a large estate that can take minutes, and it is not practically reversible.

Security: replace exposed tokens

In 4.7.0 and 4.7.1, API tokens created through background bulk requests were recorded in plaintext in job results, readable by anyone who can view jobs. 4.7.2 rejects such requests. Treat any token made that way as exposed and replace it.

If you restored a database from a v4.7.0 dump

The triggers that cascade hierarchical paths were not recreated by that restore, so renaming or moving a region, location, tenant group or similar did not update its descendants. Upgrading reinstalls the triggers but does not repair values already stale. The documentation has a procedure to detect and correct them.

Model·Hardware templates

Define a model of hardware once. Every device inherits its ports.

Device types are templates

A device type lists the interfaces, console ports, power ports and bays a model has. Create a device of that type and all its components appear, named and numbered. Edit the template and new devices pick up the change.

models/dcim/devicetypedevicetype-library

Modules for modular kit

Chassis with line cards, transceivers or expansion cards use module bays and module types. Installing a module can create its interfaces with the right names.

models/dcim/moduletype

New in 4.7: bay types and moves

Module bay types declare what fits where, for example an SFP28 cage or a PCIe x16 slot, and NetBox validates that a module suits its bay. An installed module, with its whole subtree, can now be moved to another bay instead of being deleted and recreated.

New in 4.7: lifecycle date

Device types and module types gain an end_of_life date. Filter on it and you have a hardware refresh list without a separate spreadsheet.

Model·Clusters and virtual machines

Hypervisors are devices. Guests are virtual machines, on the same IP plan.

Clusters

Group hosts into a cluster of a type you define, for example VMware, Proxmox or Kubernetes, optionally scoped to a site. Hypervisors stay ordinary devices in racks.

models/virtualization/cluster

Virtual machines

Record vCPUs, memory, disks, role, platform and status. Give them interfaces and assign IPs from the same prefixes your physical kit uses.

models/virtualization/virtualmachine

One search for everything

Search an IP address and find the VM, its cluster, the host it sits on and the rack that host is in. That chain is the whole point of modelling both sides.

Be honest about scope: community NetBox stores what you tell it. It does not read vCenter or a cloud account for you. Teams populate it from their platform with scripts or the API, which the integration chapter covers.

Operate·Customisation

Bend the model to your estate without forking anything.

Custom fields

Add your own attributes to almost any object: text, integer, boolean, date, URL, JSON, a pick list or a reference to another object. They show in the UI, filters, exports and both APIs.

4.7: selection fields now return both the raw value and its label in REST and GraphQL, for example {"value": "datacenter", "label": "Data Center"}.

customization/custom-fields

Tags and config contexts

Tags label anything for filtering. Config contexts attach JSON data to devices and VMs by site, role, platform, tenant or tag, then merge it, which is how you hold NTP servers or syslog targets once.

4.7 pre-renders and caches the merged result per device and VM.

features/context-data

Make the UI fit

Custom links jump from an object to your other tools. Export templates render data in any text format. Saved filters and dashboards give each team their own starting view.

custom-linksexport-templates

Config templates

Write a Jinja2 template once, attach it to a device or role, and NetBox renders that device's configuration from its own data and merged config context. Rendering is core. Pushing the result to the device is left to your automation.

curl/api/

     -H "Authorization: Bearer $TOKEN" \

     --data '{"description": "Primary DC"}'

Tokens

Create one on your profile page. The server generates it, you cannot choose it, and you can only see it once, so store it straight away. A token can be read-only or write-enabled.

Bulk writes, 4.7 style

Send a list to a list endpoint to create or update many objects. Append ?background=true to run it as a job. A 202 only means accepted, so check the job's final status.

Explore it

Your instance serves interactive API docs at /api/docs/.

Operate·Python inside NetBox

A custom script is a Python class that runs with full access to your data.

scripts/offline_devices.pypython
from dcim.choices import DeviceStatusChoices
from dcim.models import Device
from extras.scripts import Script


class OfflineDevices(Script):
    class Meta(Script.Meta):
        name = "Offline devices"
        description = "Flag devices marked offline"

    def run(self, data, commit):
        offline = Device.objects.filter(
            status=DeviceStatusChoices.STATUS_OFFLINE
        )
        for device in offline:
            self.log_warning(
                f"{device.name} is offline", device
            )
        self.log_success("Check complete")

Where it goes

Drop the file into the scripts volume. In netbox-docker that is netbox-scripts-files, mounted into the container.

Ways to run it

From the UI with generated input forms, from the REST API, or as a reaction to an event rule. From 4.7 the REST route needs a write-enabled token.

What people build

Provisioning wizards, bulk rack builds, consistency reports and data clean-ups, all using the same models NetBox itself uses.

Event rules and webhooks turn a change in NetBox into a ticket, a pipeline run or a chat message.

Govern·Accountability

Every change is recorded, with the before and the after.

What gets logged

Each create, update and delete stores a serialised copy of the object from before and after, plus the time and the user. Bulk edits create one record per object, tied together by a request ID.

Say why

Users can attach a message of up to 200 characters to a change, in the UI or the REST API. It is the cheapest audit trail you will ever get.

Get it out

Browse it in the UI, export it as CSV, or read it from the API at /api/extras/object-changes/.

Retention is finite

Changes are kept for 90 days by default, controlled by CHANGELOG_RETENTION. Set it to 0 to keep them for ever. If an audit needs a year of history, change it before you need it, not after.

More than a log

Journal entries hold human notes on an object. Notifications and subscriptions tell people when something they care about changed. Event rules can act on the same snapshots.

source: change logging · configuration: CHANGELOG_RETENTION

Govern·Who can do what

Grant access by object, not just by page, and sign in through your identity provider.

Object-based permissions

A permission names the actions allowed (view, add, change, delete, or custom ones) on certain object types. Optional JSON constraints narrow it to a subset, for example only devices at one site or owned by one tenant.

administration/permissions

Tenancy

Tenants and tenant groups say who owns racks, devices, prefixes, circuits and VMs. Combined with constraints, a team can see and edit only its own estate.

features/tenancy

Single sign-on

The netbox-docker override example carries Okta OpenID Connect and Google OAuth2 settings, and the configuration folder has an LDAP slot. Local accounts still work for break-glass access.

API tokens

Tokens map to a user and inherit that user's permissions. They can be marked read-only, and in 4.7 a token needs write ability to execute a custom script over REST.

Test SSO before you upgrade

4.7 upgraded the social-auth libraries by a major version each. Try your login flow on a non-production copy first.

Govern·Day-2 operations

Back up the database and the volumes, and rehearse the restore.

backuppostgres
# Dump the database (name and user come from env/postgres.env)
docker compose exec -T postgres \
  pg_dump -U netbox netbox | gzip > netbox-$(date +%F).sql.gz

# Then copy these volumes too
#   netbox-media-files

#   netbox-reports-files

A backup you have not restored is a hope

A restore of a v4.7.0 dump skipped recreating hierarchical-path triggers and still reported success. Restore to a scratch instance and check that renaming a region updates its children.

Health

The web container has a health check and the worker checks that rqworker is running. docker compose ps shows both. Allow about 90 seconds on a normal start, longer after a major upgrade.

Metrics

Prometheus-style metrics are off by default, via METRICS_ENABLED=false in the env file. Turn them on if you want to graph NetBox itself.

Upgrading

  • Read the release notes between your version and the target
  • Let background queues drain, so no stale webhook jobs are in flight
  • Bump VERSION and check out the matching netbox-docker tag together
  • docker compose pull && docker compose up -d

The housekeeping command was removed in 4.7. If you schedule it yourself, move to the individual management commands.

Use case 02·IP address management

Stop picking addresses by eye. Ask NetBox for the next free one.

curlREST
# Next free address in prefix 42
curl -s -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  "$NETBOX/api/ipam/prefixes/42/available-ips/" \
  --data '{"description": "web-01",
           "status": "active"}'

# Next free /28 inside container prefix 7
curl -s -X POST \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  "$NETBOX/api/ipam/prefixes/7/available-prefixes/" \
  --data '{"prefix_length": 28}'
pynetboxpython
prefix = nb.ipam.prefixes.get(42)
ip = prefix.available_ips.create(
    {"description": "web-01"}
)
print(ip.address)

Why it is safe

Allocation takes a lock inside NetBox, so two pipelines asking at the same moment do not receive the same address.

Same idea for other pools

IP ranges expose available-ips, VLAN groups expose available-vlans and ASN ranges expose available-asns.

Use case 06·Network automation

Render each device's intended configuration from NetBox, then push it with your own tooling.

Source of truthNetBoxDevices, interfaces, VLANs, config context
Core featureConfig templateJinja2, rendered per device
Your toolingPipelineAnsible, Nornir or CI
TargetNetwork deviceReceives the config

Where NetBox stops

NetBox renders the text. Delivering it, validating it and rolling it back are jobs for the pipeline you already trust.

Hold shared values once

NTP, syslog and AAA servers live in config contexts by region or role. Change one record and every affected device renders the new value.

Trigger it on change

An event rule can start the pipeline when a device moves to active, or when an interface description changes.

Use case 07·Keeping the record honest

NetBox holds the intended state. You bring the observed state and compare.

1ObserveMonitoring, a script or your own discovery tooling reports what is actually there.
2CompareRead the matching objects from NetBox over the API and diff them.
3DecideIs the device wrong, or is NetBox out of date?
4ActRaise a ticket, fix the device, or update NetBox. The change log records the update.

Examples teams automate

  • Neighbours seen by LLDP versus cables recorded in NetBox
  • Addresses answering on a subnet versus addresses allocated
  • Hosts reported by a hypervisor versus VMs recorded

Be clear about the boundary

Community NetBox does not discover or poll anything. The observed side comes from tools you provide. NetBox gives you a trustworthy other side to compare against.
